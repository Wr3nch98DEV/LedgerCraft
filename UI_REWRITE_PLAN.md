**Deviations from the plan, for review:** the UI lives in one crate (`crates/ledger-app`, modules per area) rather than four, and talks to the engine through the existing in-process command dispatcher (`ledger_server::rpc::handle`, same as the REST API) rather than new typed calls. Both kept the prototype fast to build and can be split/typed later without changing screens. The layout preference is stored per computer (`ui-preferences.json`), not yet per user.

**Tests:** 9 native-app tests (money/date parsing, invoice editor → engine round trip, bank-feed actions reconcile the demo feed to zero difference, every report runs from the viewer, form payloads) + 46 engine tests.

**Status:** draft for review. No code changes until approved.
**Goal:** replace the web UI (Svelte/TypeScript/HTML/CSS shown in an Edge/Chrome window) with a native desktop UI written entirely in Rust using **iced**. The UI ships with two switchable layouts:

1. **QuickBooks-style** (built first)
2. **Xero-style** (built second)

Both layouts run on the same accounting engine, data file and rules. Switching layouts never changes the books.

## 1. What changes and what stays

| Part | Today | After the rewrite |
|---|---|---|
| Accounting engine `ledger-core` (ledger, tax, payroll, reports, banking, 49 tests) | Rust | **Unchanged**, plus the additions in §6 |
| Data file (`.lcdb`, SQLite) | Rust + SQL | **Same file.** Existing organisations open in the new app. New tables come in as normal migrations. |
| Desktop UI (80 screens) | Svelte / TypeScript / CSS in a browser window | **Rust (iced)**, a native window with no browser |
| Invoices, statements, payslips, reports for printing | HTML, then print-to-PDF | **PDF generated directly in Rust** |
| Emails | Text + HTML attachment | Text + **PDF attachment** |
| Local REST API, webhooks, background jobs | Rust (axum) | Kept as a headless service inside the app (no UI) |
| Customer-facing online invoice / quote-accept page | HTML generated by Rust | **Your decision**, see §3 (D2) |
| `start.bat` | npm build + cargo build | **cargo only.** Node/npm no longer needed. |

The UI code will be 100% Rust. SQL remains only as the database schema and the queries inside the Rust engine; it is a storage format, not a UI language.

## 2. Why iced, and its known limits

iced 0.14.0 (released 7 Dec 2025) is the current stable version. It adds a built-in **table widget**, **headless testing** and **end-to-end testing** support, all of which this plan relies on. iced is pure Rust, renders on the GPU (wgpu) with a software fallback, and its Elm-style architecture (state → message → update → view) suits a forms-heavy accounting app. iced has no stable 1.0; we pin **0.14.x** and upgrade deliberately.

Gaps we will have to fill ourselves (budgeted in Phase 0–1):
- An editable spreadsheet-style **line-item grid** (Tab/Enter navigation, autocomplete cells).
- A **date picker** (`iced_aw` has one; we confirm it works with 0.14, otherwise we build a small one).
- **Charts** (bar, pie, line) drawn on iced's canvas.
- **Virtualised long lists**, so 100,000 transactions scroll smoothly.
- **Screen-reader support** is limited in iced today. Keyboard navigation will be complete, but screen-reader support will lag behind the web version. This is the main thing the move to native loses.

## 4. Architecture

### 4.1 Crates

```
crates/
  ledger-core/        unchanged engine (+ §6 additions)
  ledger-server/      becomes a library: REST API, webhooks, online invoice page, jobs (no UI)
  ledger-app/         NEW  the desktop binary (iced). Single .exe, starts the window + background service
  ledger-ui/          NEW  layout-independent UI logic: app state, backend bridge, screen models,
                           validation, formatting, vocabulary, navigation model, theme tokens
  ledger-widgets/     NEW  reusable iced widgets: data table, line-item grid, autocomplete,
                           date picker, money input, modal, toast, menus, tabs, charts, palette
  ledger-pdf/         NEW  PDF rendering: invoices, quotes, POs, credit notes, statements,
                           payslips, remittances, reports, (later) cheques
  skins/
    quickbooks/       NEW  QuickBooks-style shell, navigation and screen views
    xero/             NEW  Xero-style shell, navigation and screen views
```

### 4.2 How the UI talks to the engine

- The engine's database connection isn't thread-safe to share, so it lives on **one backend worker thread** (an "actor").
- UI screens send typed commands, e.g. `Backend::SaveInvoice(DocInput)`, through a channel and receive results as iced messages. No HTTP and no JSON in between: the UI calls the engine's Rust functions with the engine's own Rust types.
- Long jobs (imports, reports over 100k rows, ECB rate fetch, SMTP) never block the window. They run as iced `Task`s that report progress.
- The REST API / webhook / online-invoice service runs on its own thread with its own connection to the same file. SQLite WAL mode handles concurrent access safely, as today.

### 4.3 One set of logic, two looks

Every screen is split into two parts:

1. **Screen model** (in `ledger-ui`, shared): the state, messages, `update` function, validation and engine calls. Example: `InvoiceEditor` knows about lines, totals, tax, approval and saving.
2. **Skin view** (in `skins/quickbooks` and `skins/xero`): only the `view` function. It decides where things go and what they're called.

This keeps the accounting behaviour identical in both layouts, and tests on the screen models cover both. Where the two products have genuinely different workflows (e.g. QuickBooks' Undeposited Funds and cheques, Xero's statement-line reconcile), the engine supports both and each skin exposes its own entry points.

**Vocabulary layer.** Every user-facing term goes through a lookup, so the same screen model reads naturally in each layout:

| Concept | QuickBooks-style | Xero-style |
|---|---|---|
| Customer / supplier | Customer / **Vendor** | Contact (customer / supplier) |
| Quote | **Estimate** | Quote |
| Credit note (sales) | **Credit memo** | Credit note |
| Supplier credit | **Vendor credit** | Credit note (bill) |
| Spend money | **Expense** / **Check** | Spend money |
| Receive money | **Sales receipt** / **Deposit** | Receive money |
| Manual journal | **Journal entry** | Manual journal |
| Tracking categories | **Class** and **Location** | Tracking categories |
| Items | **Products and services** | Products and services |
| Bank reconciliation (matching bank lines) | **Banking → For review** | Reconcile |
| Statement tick-off reconciliation | **Reconcile** (ending balance) | Reconciliation report |
| Tax | **Sales tax** (US) / GST / VAT by country | GST / VAT by country |
| Repeating | **Recurring transactions** | Repeating |

### 4.4 Theme and look

- Design tokens (colours, spacing, radii, type scale) per skin, each with dark and light variants. Today's dark palette carries over to the Xero-style skin. The QuickBooks-style skin gets its own palette: green accent, white-card layout feel, in dark and light.
- Font: **Inter** (open licence), bundled. Icons: **Lucide** (open licence) SVGs, rendered by iced's built-in SVG support.
- Window: remembers size and position, minimum width ~1024 px. The sidebar collapses on narrow windows.

### 4.5 Printing and PDF

- `ledger-pdf` lays out documents in Rust and writes PDF files. Phase 0 compares PDF crates (e.g. `krilla`, `printpdf`) on Unicode text, embedded fonts, images (logos) and output size.
- "Print" opens the PDF in the system viewer, which provides the OS print dialog. "Save as PDF" writes the file directly.
- Branding themes (logo, accent colour, titles, payment details, terms) apply to all PDFs, as today.

### 4.6 Background jobs (unchanged behaviour)

Repeating transactions, payment reminders, SMTP sending, webhook delivery, ECB rates, daily automatic backups. They move into `ledger-server` as a library started by `ledger-app`.

## 6. Engine additions needed for QuickBooks workflows

Each addition gets its own migration (`schema_v5…`), integration tests, and is added to the property test, so the "ledger always balances" guarantee covers it. All of them are also available to the Xero-style layout and the API.

1. **Undeposited Funds + Bank deposit.** System clearing account. "Receive payment" and "Sales receipt" can deposit to Undeposited Funds; a **Bank deposit** groups them (plus extra lines and a cash-back line) into one bank entry that reconciles against the single bank line.
2. **Receive payment across multiple invoices.** One customer payment applied to several invoices and credit memos, with overpayment → credit. Builds on the existing batch-payment grouping.
3. **Sales receipt and refund receipt.** Sale and payment in one document (income + tax against bank or Undeposited Funds), and its reverse.
4. **Checks.** Payment method and cheque numbering on expenses and bill payments, the "To print" queue, and a printable cheque PDF (standard US voucher layout).
5. **Statement tick-off reconciliation.** Reconcile sessions (account, statement date, beginning/ending balance, cleared items, difference, finished-by/at, undo). This coexists with today's statement-line matching: an item counts as reconciled either way.
6. **Excluded bank lines** ("Excluded" tab, restorable).
7. **Delayed charge / delayed credit.** Non-posting entries that can be pulled into a later invoice.
8. **Account detail types.** A QBO-style detail type on each account, mapped onto the existing account types (no change to posting rules).
9. **Classes and Locations.** Display names for the two existing tracking categories. No schema change beyond labels.
10. **1099 contractor tracking (US).** Vendor flag, 1099 box per account mapping, 1099 summary/detail report and export file. Filing stays "export only", like payroll.
11. **US sales tax by agency.** Tax rates grouped by agency, liability report per agency, recording a sales-tax payment.
12. **Per-user layout preference** (D7).

Excluded from this plan: QuickBooks Payments-style card processing (same plugin approach as today), "Progress invoicing", "Bundles". These can be added later if requested.

## 9. Testing and quality gates

- **Engine:** all existing tests stay green at every commit. Each §6 feature adds integration tests and joins the property test (random operations must leave debits = credits, AR/AP = open documents, balance sheet balanced on accrual and cash basis).
- **Screen models:** plain Rust unit tests of `update` functions (e.g. "typing qty 3 × rate 10 with 10% tax gives total 33.00", "approve is disabled while unbalanced").
- **End-to-end:** iced headless tests drive real flows in both layouts: create invoice → receive payment → deposit → reconcile; bill → pay bills → cheque; run each report and compare totals with the engine.
- **Cross-layout check:** the same scripted actions in both layouts must produce identical ledgers.
- **Performance targets:** cold start < 1 s; screen switch < 100 ms; smooth scrolling at 100k transactions; main reports < 1 s at 100k; release `.exe` < 25 MB.
- **Visual review:** screenshots of every screen in both themes at the end of each phase, checked against the layout spec in §5.

## 10. Risks

| Risk | Impact | Mitigation |
|---|---|---|
| iced is pre-1.0; APIs change between versions | Upgrade work later | Pin 0.14.x; keep custom widgets in `ledger-widgets` so an upgrade touches one crate |
| Missing or immature widgets (grid, date picker, charts) | Slower Phases 1–3 | Built and proven in the Phase 0 spike before any screens |
| Screen-reader support in iced is limited | Less accessible than the web UI | Full keyboard support; revisit when iced's accessibility work lands |
| Two layouts double the view code | Maintenance cost | Shared screen models + vocabulary layer; views stay thin |
| "1:1" expectations vs. not copying brand assets | Users may notice differences in colours, fonts, logos | Match structure, flow and terms exactly; keep the "not affiliated" disclaimer (D3) |
| Engine additions (§6) touch posting logic | Accounting bugs | Each addition proven by tests and the property test before any UI uses it |
| Large rewrite | Long time without a usable native build | Web UI stays available until Phase 8 (D5); every phase ends with a launchable build |
